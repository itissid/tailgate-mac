# One-Mac options: trusting an app versus approving a write

**Recommendation:** For a privately installed, no-fee Mac build, evaluate the built-in Keychain Access app and `/usr/bin/codesign` before buying or deploying another signing service. Keep one fresh operator approval over the exact policy review, not one generic password prompt for every API read. This is a proposed alternative, not a supported switch in the current live build.

## Is first-use consent enough?

For a password stored as a **file-based Keychain item**, [Apple's user guide](https://support.apple.com/guide/mac-help/kychn002/mac) offers Deny, Allow Once, and Always Allow. [Apple's ACL reference](https://developer.apple.com/documentation/security/access-control-lists) explains that trust is **per item and operation**: Always Allow adds the calling app to that operation's trusted list, normally permitting subsequent reads without another item-access prompt. Allow Once does not enroll the app; the next time the app needs to retrieve the password it must ask again. A locked keychain can still require unlocking. In Keychain Access the operator can inspect a password item's Access Control tab, select confirmation, and request the keychain password. Do not equate a legacy password-confirmation dialog with guaranteed fingerprint authentication or with consent to a particular network operation.

The live release instead uses a **Data Protection Keychain** access group. [TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains) distinguishes this from file-based ACLs and recommends the newer store for new code. A first-use user prompt does not confer an app entitlement or move an existing record into the other store. The alternative would require code and separately provisioned records. Apple also documents [user presence](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/userpresence) as an item/key constraint; it permits biometry or passcode. That is distinct from a biometric-only key operation and still does not describe which policy bytes the user saw.

## Concrete tools

- **Keychain Access → Certificate Assistant, plus `codesign`:** [Apple documents creating a self-signed identity](https://support.apple.com/guide/keychain-access/create-self-signed-certificates-kyca8916/mac). A stable Mac code-signing identity is intended to let the OS recognize successive approved builds; whether the identity satisfies a subsystem's trust policy matters ([TN2206, especially Keychain and self-signed identities](https://developer.apple.com/library/archive/technotes/tn2206/)). Protect its private signing key from the agent. Do not globally trust a new root or allow all apps access to a credential as a shortcut. Our disposable experiment has not yet demonstrated both successful owner reads and denied cross-signer reads.
- **Minisign, only if independent release verification is wanted:** the [project](https://github.com/jedisct1/minisign) signs files and verifies detached signatures against a trusted public key. An operator or installer could verify the release archive before installation. This is not a runtime Mac code signature, Keychain permission, or biometric approval; it does not replace the native identity/credential boundary. For a single Mac with a trusted local release process, omit this extra step unless there is a separate distribution requirement.

**Do not authorize the agent's shell, interpreter, or the generic `security` CLI as a trusted reader of an actual OAuth secret.** The intended reader is the approved native Tailgate process. Likewise, granting one item read cannot make an API bearer token one-use: once released into app memory, the token can authorize requests within its scope until it expires or is invalidated. The intended write gate is the reviewed-plan signature plus the app's one-use and stale-policy checks. This note describes documented behavior and design options, not an executed acceptance test or changes to local trust settings.
